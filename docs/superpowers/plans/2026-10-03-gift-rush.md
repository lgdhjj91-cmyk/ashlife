# Ashlife Gift Rush Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a cute, mobile-first 90-second gift-packing game with Practice, Daily challenges, safe Joy Coin claims, and a collectible sticker to Ashlife Playroom.

**Architecture:** Pure JavaScript rules drive a React/HTML game, with CSS feedback and a hook managing the visible-time clock, persistence, and existing wallet calls. Reuse current product art, shared settings, album, local storage, and transactional wallet claims; lazy-load a dedicated game route. No physics engine or new product dependency is required.

**Tech Stack:** React 19.2, Vite 5, React Router 7, CSS, existing Firebase wallet repository, Node's test runner, existing Vite SSR test pattern.

**Spec:** [Gift Rush design](../specs/2026-10-03-gift-rush-design.md).

**Status:** Plan only; implementation has not started. The user selected the concept and requested this plan. Gameplay numbers and artwork direction remain reviewable defaults. Native execution is the suggested approach for this small game; the header lists the available workflows, not authorization to dispatch workers now.

## Global Constraints

- The round always lasts 90 seconds of active play.
- Product supply is unlimited.
- Keep storage key `ashlife-playroom-v1` and version 1.
- Completing that day's objective awards exactly **20 Joy Coins once per wallet and date**, using claim ID `gift-rush-daily:<dateKey>`.
- Practice awards zero coins.
- Asset paths use `import.meta.env.BASE_URL` so both the custom domain and `/ashlife/` hosting work.
- Gift Rush requires no collision simulation, so it introduces no Phaser or Three.js runtime and no new product dependencies.
- Use the existing browser-local `getLocalDateKey` convention and capture the date once at round start.
- Bind a pending reward to the wallet UID that earned it.
- Add it only to the album's complete `stickers` array, never to `memoryMatchStickers`; provide its English and Chinese album names.
- Controls are real buttons with at least 44 × 44 CSS-pixel touch targets, visible keyboard focus, text labels, and keyboard activation through Tab/Enter/Space.
- Implementation completion requires browser evidence and a short balance playtest; unit tests alone cannot establish that the game is fun.

## Review Focus

1. Pack tapped twice, callbacks arriving after Replay, and expired-order actions: one delivery and one result application only. Task 2 transition tests; Task 5 lifecycle playthrough.
2. Incorrect quantities and wrong wrapping, including two of one product: exact multiset matching, editable per-customer trays, recoverable mistakes. Tasks 1–2 tests and Task 5 playthrough.
3. Slow frames, hidden tabs, and midnight: stable deadline ordering, explicit Resume, and reward date captured at start. Task 2 clock tests and Task 5 browser checks.
4. Reward call fails or response is lost, reload occurs, or the wallet changes: persistent pending reward, stable claim ID, no optimistic credit or cross-wallet transfer. Tasks 3 and 6 tests.
5. Old/malformed storage and missing artwork on narrow screens: previous game data survives; labeled fallbacks and operable controls remain. Tasks 3–4 tests and Task 7 browser checks.

## Shared contracts

Use plain JavaScript objects; these shapes describe interfaces rather than introducing TypeScript.

- `ProductId`: one of `bear-notebook`, `bunny-pencil-case`, `bear-heart`, `bubble-tea-keychain`, `paw-squishy`, `kawaii-washi-tape`.
- `CustomerId`: `bunny | bear | chick`. `WrapId`: `pink-hearts | lavender-stars | mint-dots`.
- `Order`: `{ id, customerId, items: ProductId[], wrapId, initialPatienceMs, remainingPatienceMs, failedAttempts, tray: { items: ProductId[], wrapId: WrapId|null } }`.
- `RoundState`: `{ sessionId, mode, dateKey, seed, rngState, orderIndex, status, elapsedMs, nextArrivalMs, orders, selectedOrderId, stats, result }`. Status is `idle | running | paused | finished`.
- `Stats`: `{ score, servedOrders, perfectOrders, failedPackAttempts, expiredOrders, unfinishedOrders, combo, maxCombo }`.
- `RoundResult`: `{ sessionId, mode, dateKey, challengeId, stats }`; returned only by a finished state.
- `RewardClaim`: `{ dateKey, amount: 20, ownerUid: string|null }`, stored under its fixed claim ID.
- `ClaimAttemptResult`: `{ status: 'credited'|'pending'|'wallet-changed'|'unbound', claimId, ownerUid, error?: string }`.

## Task 2: Build the pure round engine and deadline handling

## Dependency order and review checkpoints

Task 1 → Task 2 establishes the game. Task 3 implements records against the stable result shape. Task 4 supplies art/copy. Task 5 builds the counter; Task 6 completes rewards. After building Task 5's page, perform Task 7's first route/card step, then finish Task 5 browser verification and commit the page together with that route/card wiring. Task 6 can now be verified through the real route. Finally finish Task 7's remaining responsive/build/playtest steps. This deliberate overlap avoids a temporary production route or a separate test app and makes each UI deliverable reviewable.

Review a functional counter before polishing art, then review the phone layout before calling the game complete. An implementation skill for React work should be loaded at execution time. The game is 2D HTML, so do not scaffold a Three.js project or import a physics engine merely because other Playroom games use Phaser.
